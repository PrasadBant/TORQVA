## Defect found and fixed this run (root cause of the latched SENSOR_INVALID)
`SafetyMonitor::update` treated "voltage invalid" as a critical sensor fault, and `main.cpp` marked any bus voltage at or below 1 V as invalid. With the motor supply off, a working INA219 reads 0 V, so the board latched `SENSOR_INVALID` within 500 ms of boot. The default `volt_min_v` (20 V, an unapproved assumption) would also have tripped `VOLTAGE_LOW` if 0 V had been accepted.
Fix: 0 V from a responding INA219 is a valid measurement (a non-responding or non-finite one is still invalid and still latches). An absent supply (below `kSupplyPresentV` = 1 V) with the drive idle is no longer a fault; low voltage while driving, or a present-but-low supply, still trips; and a new start interlock `SUPPLY_NOT_PRESENT` refuses motion. Tests: native (`test_absent_supply_while_idle...`, device-level idle test, interlock reason) and backend. **The board still runs the previous firmware: this fix is not on it until a new, separately authorised flash.**

## Phase 38 - runtime-configurable limits over the authenticated protocol
**Design (implemented):** the operator approves limits in Safety & Commissioning (current, min/max supply voltage, temperature, rpm, duty). The backend validates (finite numbers, ranges, completeness, min below max, ceilings equal to the firmware's MEASUREMENT ratings: INA219 3.2 A / 26 V, DS18B20 125 C, Hall 30 000 rpm, duty 100 %), requires the typed phrase `APPROVE THESE LIMITS`, assigns a version, and records who, when, previous and new values (history, last 50). Approving new limits clears the commissioning enable. After the authenticated session exists, the backend pushes the limits as a `cfg` message MAC'd with the session key (device-bound through the per-device key and device id; sequence counter = replay protection; version must increase). The firmware validates again, applies them to the safety trips, the duty cap and the rpm cap, replies `cfg_ack`, and reports the accepted version in the status frame (`cfg`). Motion needs a configuration accepted in THIS boot (`LIMITS_NOT_APPROVED` otherwise); a copy stored in NVS is restored after a reboot only so the trips use the approved numbers, it never approves motion, and the backend re-sends over the new session. Missing, invalid, unauthenticated or stale configuration keeps motion refused and nothing is defaulted. The limits row of the interlock table is VERIFIED only when the device-confirmed version equals the approved version.
**Files:** firmware `lib/torqva_core/runtime_config.{h,cpp}`, `auth.{h,cpp}` (`verify_message`), `device.{h,cpp}` (`handle_cfg`, `restore_runtime_limits`, interlock), `protocol.{h,cpp}` (`cfg` in status), `src/main.cpp` (NVS persistence/restore), `tools/fitl_cli.cpp` (frame buffer 320: a status frame with `cfg` was truncated at 256 by the CLI); backend `commissioning.py`, `device_routes.py`, `serial_bridge.py` (`_cfg_tick`, `_on_cfg_ack`, `config` snapshot, blockers, interlock); frontend commissioning card (min voltage, confirmation, version/history).
**Verified in software (no hardware):** native 126/126 (new: authenticated config applies and is reported; unauthenticated, tampered, replayed, rolled-back, out-of-range and non-numeric configurations change nothing; restored configuration does not approve motion; codec and validation); backend 643 incl. the REAL firmware core accepting a Python-signed `cfg`, applying it, and refusing a corrupted one (`CURRENT_OUT_OF_RANGE`), versioned re-approval, history, confirmation phrase; frontend 81; E2E 63 checks.
**Not done (honest):** (1) latch persistence across MCU restarts and a deliberate reset procedure (a restart still clears a RAM latch; boot-reason faults still latch; there is no reset button or wired input, so a persistent latch would need that design first); (2) the firmware module split of `main.cpp` (no regression-safe refactor was done); (3) the E-stop input and reset-safe driver remain hardware prerequisites; (4) the numeric limits themselves: the equipment specifications needed are the motor's rated current and voltage, the driver (BTS7960 module) current rating and the supply's voltage/current rating; the INA219 can only measure up to about 3.2 A, so higher-current motors need a different shunt first.
**Artifacts (not on the board):** `esp32s3_uart` 360 128 bytes `050a6c23374918da999a9e61fcebddd671921e2afa64e2d2bd676dcd87780b14`; `esp32s3` 346 176 bytes `816a73474e989da15e914aa4f7b1248880218d6cf34373061d2be7d0a39e20f2`. ## Phase 42 - owner decisions: authenticated USB accepted; E-stop monitoring input on GPIO 15

## Phase 44 - remaining motor-control blockers fixed in code (NO tests were run in this phase)
**Genuine defects found and fixed:**
1. **Motor control was compiled out of every device build** (`TORQVA_CONTROL_ENABLED` unset): the firmware answered `NOT_IN_HARDWARE_CONTROL` to every START/SET_SPEED whatever else was satisfied, and nothing in the backend or UI showed it. Both device environments now build with `-DTORQVA_CONTROL_ENABLED=1` and the label key `authenticated-session-only` (with a provisioned device key the plaintext key is ignored; no session, no motion). This permits no motion by itself: limits confirmed in this boot, authenticated session, E-stop declared AND released, watchdog, valid sensors, supply, no fault and a live heartbeat are all still required. The backend now reports `ctl=0` builds as a blocker.
2. **Heartbeat dead-man would have latched at every boot once control was compiled in** (it ran from the first control iteration, before any host connected). It now applies while the motor is being DRIVEN; START still needs a recent heartbeat (`NO_HEARTBEAT`), so nothing starts without a live host, and a quiet host at idle is not a fault. A session end/replacement forgets the heartbeat; nothing here clears a trip.
3. **The backend never sent heartbeats.** It now sends an authenticated `HEARTBEAT` (MAC, session counter) every 0.5 s while a session is active and the firmware has control compiled in; their acknowledgements are not shown as command results. It never starts anything.
4. **E-stop input:** with the declaration flag set, the boot-time UNKNOWN state (first 100 ms, not yet debounced) would have latched `EXTERNAL_ESTOP` on every boot. Now only ASSERTED (pressed / open circuit / broken wire) stops and latches; UNKNOWN and ASSERTED both block a start (`ESTOP_ACTIVE`). `TORQVA_ESTOP_INPUT_WIRED` stays 0 in every build (not declared installed or verified).
**Reviewed, no defect found:** driver outputs (R_EN/L_EN/RPWM/LPWM forced LOW first in `setup()`, PWM failure keeps the driver disabled and latches `OUTPUT_INIT_FAULT`, `apply()` inhibits everything unless enabled); runtime-limit handling (authenticated, versioned, validated, stored for audit only, re-approved per boot).
**Dashboard:** chips now show the E-stop input state, the transport label, and whether the limits are confirmed by the device (with the accepted values); the first blocker and the full list are unchanged and come from the backend only.
**Direction:** not implemented (the firmware never drives LPWM); the UI only states "forward only", there is no direction control.
**Not done (reason):** persisting a latched fault across a reboot and a deliberate reset procedure. A latch is RAM-only today, so a power cycle clears it, except boot-reason faults (brownout/watchdog/panic) which latch at boot. A persistent latch needs a reset input (`LOCAL_RESET_BUTTON` is unconfigured) or an equivalent deliberate procedure designed first; building it blind (no tests this phase) risked leaving the board permanently latched. Also not done: firmware module split, removal of further commissioning UI.
**Unverified because tests were not run:** every change above (firmware 4 files, backend `serial_bridge.py`, 3 test files adjusted, new tests added but NOT executed). The previous artifacts and results no longer apply; run the suites before relying on this. The board still runs the previous firmware.
