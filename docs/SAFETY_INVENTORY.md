# Safety and access inventory

The deployed ESP32 image enforces motor protection locally. Backend checks decide whether to forward a request and report the device's current state. The browser presents those facts and sends authenticated operator requests.

| Classification | Mechanism | Owner and effect |
| --- | --- | --- |
| SAFETY_CRITICAL | Independent emergency power cut-off | Physical circuit upstream of the BTS7960. Commission on the bench. The GPIO contact gives the ESP32 a separate status input. |
| SAFETY_CRITICAL | E-stop input and latched shutdown | `firmware/lib/torqva_core/safety/estop.*`, `safety.*`, `interlock.*`, and board input wiring in `firmware/src/main.cpp`. An asserted or unread monitored contact stops drive. The stock profile reports an unverified circuit and inhibits start. |
| SAFETY_CRITICAL | Reset behavior and watchdog | `firmware/src/main.cpp` turns outputs off at startup, latches an output initialization fault on PWM failure, and stops driving when the control task cannot acquire its lock. The board watchdog and reset-fault handling remain local. Fault reset requires an authorized request and the applicable local reset input. |
| HARDWARE_PROTECTION | Current, voltage, temperature and critical sensor validity | `firmware/lib/torqva_core/safety/safety.cpp` enforces instantaneous/sustained overcurrent, supply window, temperature, sensor loss and configured optional protection. Drive and PWM stage also clamp duty to the operating envelope. |
| HARDWARE_PROTECTION | Hall pulse loss and speed envelope | `safety.cpp` detects loss of pulses above the configured duty. The configured RPM ceiling limits commands. Independent overspeed protection and driver fault wiring require bench evidence. |
| HARDWARE_PROTECTION | Host heartbeat and session dropout | Firmware checks fresh heartbeats before start and during drive. Communication loss trips or drops drive locally. Reconnection does not replay commands. |
| HARDWARE_PROTECTION | Firmware update and recovery | Firmware refuses motion during an active or unconfirmed OTA update. Eligibility checks require idle state and safe supply readings, with separate LED-only bench capability. The boot self-test and rollback are enforced on the device. |
| COMMAND_VALIDATION | Firmware arming prerequisites | Initialization, validated operating limits, compatible control profile, verified E-stop monitoring, watchdog, required sensors, supply, freshness and heartbeat are checked in `interlock.cpp` and `shared/device.cpp`. Authentication is tracked as its own prerequisite. |
| COMMAND_VALIDATION | Request and device validation | `backend/torqva/api/device_routes.py` validates input shape. `control/commands.py` checks values, operating envelope and unsupported durations. Firmware validates command type, bounds, sequence, TTL, session and duplicate IDs. STOP stays available through firmware fault and session states that refuse motion. |
| COMMAND_VALIDATION | Telemetry quality and link liveness | `backend/torqva/device/wire_protocol.py` validates frame shape, field type, range and protocol version. `telemetry/device_state.py` tracks origin, validity and freshness. Transport, handshake and acknowledgement timeouts report failures; they do not imply a physical outcome. |
| AUTHENTICATION | Browser and API token | `backend/torqva/access/auth.py`, API dependencies and first browser WebSocket message. `frontend/src/access/` handles sign-in and session storage. |
| AUTHENTICATION | Physical device session and secure Wi-Fi | `access/device_keys.py`, `device/serial_bridge.py` and firmware `communication/auth.*` handle challenge-response, session binding and replay protection. The firmware Wi-Fi link uses its provisioned TLS CA. |
| AUTHORIZATION | Motor operation, fault reset, setup and admin actions | Operators and admins can send normal commands. All signed-in roles retain STOP. Emergency fault reset, manual serial setup, operating limits, and firmware administration have their existing role requirements. Checks live in `access/auth.py` and `api/`. |
| COMMAND_VALIDATION | Firmware artifact integrity and signed release admission | `device/firmware/` validates upload size, format, chip identity, hash and release signature. Firmware independently verifies OTA artifacts and validates compatible profiles. |
| CONTROL_OWNERSHIP | Single active physical transport | `device/serial_bridge.py`, `device/device_link.py`, `device/autoconnect.py` defend one bridge writer, one port, and one device session. Discovery claims neither a session nor an identity. |
| DIAGNOSTIC_RESTRICTION | Diagnostic preemption and cancellation | `control/manual.py` invalidates later diagnostic steps when a manual command intervenes. Firmware cancels a running diagnostic before applying a manual command. Diagnostic start also checks its own operating envelope. |
| WORKFLOW_RESTRICTION | Workflow authorization, approvals and receipts | `backend/torqva/legacy/workflow.py` and simulation analysis coordinate explicitly requested diagnostic and recovery workflows. Manual commands enter through their own API route. |
| LEGACY_RESTRICTION | Simulated dispatch and old secure transport foundation | `legacy/supervisor.py`, `dispatch.py`, `device_protocol.py` and `device_transport.py` retain their tested proposal and gateway contracts. The live USB/Wi-Fi bridge uses the current JSON-lines protocol. |
| AI_RESTRICTION | Model confidence, evidence and recommendation gates | `analysis/`, `simulation/`, and `legacy/gate.py` own prediction eligibility, confidence and workflow policy. They supply advice or simulation decisions. |
| UI_RESTRICTION | Readiness, role, stale data and request state | `frontend/src/control/MotionPanel.jsx`, `device/`, `telemetry/`, and `safety/` show disabled controls and explain owner, link, safety and input conditions. These controls are backed by API and firmware checks. |

## Shutdown evidence

The dashboard distinguishes a firmware fault, an operator STOP, telemetry timeout and device disconnection. Device telemetry carries the firmware stop reason and fault mask. Command timeouts and diagnostic cancellation have their own outcomes. A sent command is a transport event. Shaft behavior requires valid measurements or bench observation.
